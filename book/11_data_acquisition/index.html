    5　获取语料与记录来源¶

    模型还没有开始训练，实验就已经开始了¶

    假设两位同学用同一个下载地址、同一份训练代码和同一个随机种子训练模型，得到的验证损失却不同。排查很久以后，他们发现：其中一人下载数据时，发布方刚刚替换过压缩包。两份文件都叫 corpus.jsonl.gz，里面的文档却不完全一样。模型实现没有出错，实验的输入已经改变了。

    上一章讨论了数据分布为什么影响模型。本章把问题向前推进一步：怎样让“我们使用了哪些数据”成为别人能够检查的事实？为此，获取语料不能只留下下载命令。我们需要保留实际收到的文件，说明文件从哪里来、属于哪个版本，并建立从原始文件到训练输入的追踪关系。

    这件事很像实验室接收样品。试剂瓶的标签、采购批次和瓶中实际物质是三个相关但不同的对象。标签可以帮助寻找样品，批次可以解释来源，检测结果可以检查内容。数据也一样：URL 是位置，发布版本描述上游的一次发布，文件摘要用于比较收到的字节。三者互相补充。

    本章先用仓库里四条原创短文做实验。它足够小，可以逐行查看，也不需要访问外部数据服务。实验要验证的是文件身份和来源记录；它不会模拟一个已经完成许可审核或质量筛选的大规模语料库。

    从文件字节，到文档记录¶

    计算机保存文件时，保存的是字节序列。一个字节有 8 个二进制位，可以表示 0 到 255 的整数。UTF-8 等编码规则负责把文字转换成字节；JSON 等格式规则则负责说明这些文字怎样表示字段和值。理解这两层，就能区分“文件完全一样”和“文件表达了相同记录”。

    例如，下面两行 JSON 表达同一个对象，但空格数量不同：

    {"id":"d1","text":"A cat."}
{"id": "d1", "text": "A cat."}

    如果分别将它们保存成文件，字节内容不同；用 JSON 解析器读入后，得到的 id 和 text 字段相同。这里的解析就是按照格式规则，把字符转换成程序中的字典、列表或数值。它不负责判断正文是否有价值。

    格式规则还需要消除歧义。如果同一个对象写成 {"text":"第一份正文","text":"第二份正文"}，Python 默认只保留后一个值，第一次出现的正文就不在解析结果里了。本书的获取程序因此拒绝同一对象内重复的字段名，包括嵌套元数据中的重复；这不同于检查整份文件里的文档 ID 是否重复。我们是在选择明确的输入约定，不是把解析器默认的“取最后一个”误当成来源文件只有一份正文。Python JSON 的重复字段行为

    JSONL 是一种适合流式处理的组织方式：每个非空物理行放一个 JSON 对象。正文里的换行写成 JSON 字符串中的 \n 转义，而不是把一个对象任意拆成多行。本书的小实验允许空行并在解析时跳过它们。因此，给文件末尾增加一个空行，会改变文件字节，却不会增加一条文档。这个小变化正好可以帮助我们观察两种身份的区别。

    实际获取阶段通常还多一层压缩：下载到的 .gz 是一个对象，解压后的 JSONL 是另一个对象。重新压缩可能改变压缩文件而不改变解压内容。保存摘要时必须说明摘要针对哪一层，不能拿压缩包的摘要与解压文件的摘要比较。

    摘要能回答什么问题¶

    把文件字节记为 \(b\)。SHA-256 把任意长度的字节输入映射成 256 位的结果：

    \[ h=\operatorname{SHA256}(b). \]

    通常将结果写成 64 个十六进制字符，因为每个十六进制字符表示 4 位。这个字符串叫摘要。它很短，适合放进清单中。Python 标准库提供了 hashlib.sha256，不需要为计算摘要安装训练框架。

    这里有一个容易说反的逻辑。相同字节必然产生相同摘要，所以摘要不同足以说明字节不同；摘要相同则不能构成字节完全相同的数学证明。可能的文件数量超过有限个摘要，因此理论上一定存在碰撞，也就是不同输入得到同一摘要。在一般实验文件校验中，SHA-256 摘要是一种实用的完整性检查；如果要在小型实验中直接证明两份内容相同，也可以直接比较字节。

    摘要同样不说明文件从谁那里来。如果我们同时从一个错误的位置得到文件和所谓的“正确摘要”，两者一致仍不能确认发布者身份。可核对的发布页面、固定版本和可靠获取渠道承担的是来源问题，摘要承担的是内容比较问题。

    一个最小的计算片段如下：

    import hashlib
from pathlib import Path

data = Path("examples/sample.jsonl").read_bytes()
print(len(data))
print(hashlib.sha256(data).hexdigest())

    read_bytes() 读取实际字节；len(data) 是字节数；hexdigest() 返回可打印的摘要。这段代码把整个小文件读入内存，适合本章示例。面对大文件，应分块调用 update()，并记录分块读取的是同一个完整对象；没有必要为计算摘要把数百 GB 文件全部放入内存。

    做一次保留原件的获取实验¶

    在仓库根目录、已经准备好的环境中运行：

    .venv/bin/python examples/book/acquisition_walkthrough.py \
  --input examples/sample.jsonl \
  --output outputs/book-acquisition-v1

    脚本仅依赖 Python 标准库，不需要 GPU 或模型权重。它先严格读取输入中的 id 和 text，要求文档 ID 唯一，再将原字节复制到 raw.jsonl。随后，它创建一个额外增加换行字节的副本，并重新读取两个落盘文件计算摘要、解析记录并核对内容。原始输入不会被修改。默认样例已有行末换行，因此新增字节形成一个空行；如果换成没有行末换行的输入，则只是补齐最后一行的结束符。两种情况都增加一个字节，而不增加文档。

    文件 保存什么 用来回答什么
    raw.jsonl 本次获取的原始字节副本 当时实际拿到了什么？
    with-extra-newline.jsonl 只增加一个换行字节的对照副本 字节改变是否一定意味着记录改变？
    source-record.json 摘要、字节数、记录数和脚本身份 怎样核对本次观察？

    对仓库默认输入，报告应满足以下关系。这里列的是可由输入和程序推导的验收条件，完整摘要以实际运行文件为准。

    {
  "records": 4,
  "byte_counts_differ_by": 1,
  "same_parsed_records": true,
  "different_byte_digest": true,
  "original_preserved": true
}

    same_parsed_records 比较的是两个落盘文件重新解析后的完整对象列表，而不只是正文数量；修改一条正文，不能靠保持“四条记录”蒙混过关。original_preserved 来自对原始输入和落盘副本的字节比较；脚本还核对对照副本确实只追加了一个换行字节。检查失败会报错，不会仍然写出一份声称通过的报告。

    报告中的 source_id 是由输入摘要生成的本地内容标识，方便区分这次实验读取的对象；它不冒充外部数据集的发布名称。observed_at_utc 记录观察时间，每次运行通常不同。repository_commit 在 Git 检出目录中记录当前提交；从不带 Git 元数据的压缩包运行时为 null。报告还保存脚本自身的摘要，因为未提交的脚本修改不会反映在提交号中。

    因此，复现并不要求两份报告的时间字段相同。需要比较的是固定输入、处理程序和规则所决定的结果。脚本拒绝覆盖已有输出目录；再次运行时改用 outputs/book-acquisition-v2，即可保留两次独立记录。

    把本地记录扩展为真正的来源清单¶

    本地复制实验已经建立了最基本的关系：输入对象、处理动作、输出对象。对于外部语料，还要补充上游事实。可以把来源信息与文件信息分成两层。

    来源层记录谁发布、在哪里发布、使用了哪个不可变 revision 或快照、何时获取，以及条款审核依据存放在哪里。文件层记录该来源这次包含哪些实际对象，每个对象的字节数和摘要，以及获取成功还是失败。一个来源可以包含一千个文件，一个文件也可能混合多个原始来源；若有这种混合，应继续保留文档级来源字段，不能只写一个过于宽泛的文件标签。

    字段不能凭空补齐。发布方只提供会变化的“最新版”时，就记录取得时间、收到的原始对象和当时可核对的页面，而不要虚构一个不可变版本。服务返回的 ETag 可以用于其定义下的缓存判断，但具体含义依赖服务，不能一律当成内容的 SHA-256。

    本章报告将 terms_review 明确写为 not_performed_by_this_script。这是一个状态说明：计算摘要不会自动完成条款判断。正式项目应保留适用于具体来源和计划发布对象的审核记录。原始文件、清洗文本、token 分片和模型权重是不同的发布对象，不能用“数据可用”一个模糊字段代替各自的依据。本章不把示例字段当作法律结论。

    原始文件为什么要留下来¶

    设原始文件为 \(R\)，抽取程序版本为 \(e\)，清洗规则版本为 \(c\)。后续文档可以表示为

    \[ D_{\mathrm{clean}}=C_c(E_e(R)), \]

    其中 \(E_e\) 是抽取过程，\(C_c\) 是清洗过程。下标提醒我们：即使 \(R\) 不变，修改抽取或清洗规则也可能得到不同文档。

    例如，网页中有正文、导航栏和代码块。旧抽取器保留正文却遗漏代码块，新抽取器补回代码块。两次结果不同，并不说明下载文件改变了。若只保留最后的纯文本，读者无法判断代码缺失来自原网页、抽取程序还是后续过滤。

    因此，每个阶段应写到新位置，并保存输入摘要、程序和配置版本、输出摘要及数量。它们组成处理关系，而不是一份只有最终文件名的列表。发生问题时，我们可以从训练 token 追到清洗文本，再追到抽取结果和原始对象。小语料可以复制文件；大语料可以使用不可变对象存储和清单引用，原则是保留可追踪身份，不是要求每个阶段无条件复制全部字节。

    用正确的分母解释获取损耗¶

    最后看一个明确标为假设的数量例子。计划获取 1,000 个文件，其中 10 个未下载成功；已下载的 990 个文件中，10 个无法解析；剩下 980 个文件共解析出 100,000 条记录，其中 500 条缺少正文字段。

    阶段 输入单位与数量 失败或排除 交给下一阶段
    下载 1,000 个文件 10 个文件 990 个文件
    解析 990 个文件 10 个文件 980 个可解析文件
    字段检查 100,000 条记录 500 条记录 99,500 条文档

    这里不能写成“总共删除 520 条数据”：前两行的单位是文件，最后一行的单位是记录。下载成功率为 \(990/1000=99\%\)，已下载文件的可解析率为 \(980/990\approx98.99\%\)，解析所得记录的正文完整率为 \(99500/100000=99.5\%\)。每个比例回答不同问题。

    这些总体比例仍可能掩盖偏差。如果十个下载失败文件全部来自一个小语种，那么那个语种的覆盖可能损失很大。获取报告还应按来源、语言或格式拆开计数。程序故障造成的数据缺失与有意识的质量筛选要分别记录，后续才能解释模型为什么看到这样的分布。

    到这里，我们已经固定了获取对象，并能区分字节改变、解析改变和处理规则改变。下一章开始处理正文：哪些变化属于整理格式，哪些变化会删除信息，以及怎样让每次保留或拒绝都有可检查的原因。
