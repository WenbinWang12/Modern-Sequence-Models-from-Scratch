    12　数据混合：怎样决定模型读什么¶

    文件容量为什么不能替我们决定配方¶

    准备好网页、代码和书籍后，我们仍有一个没有回答的问题：在接下来的十亿个训练 token 中，各类内容应该占多少？文件都放在同一个目录里，并不意味着这个问题已经解决。

    假设网页有 900 GB、代码和书籍各有 50 GB。网页占的是 90% 的字节，不能直接推断它也占 90% 的 token。不同语言、格式和 tokenizer 的每字节 token 数可能不同。必须先用同一 tokenizer 统计 token 数，再讨论训练中的比例。下面改用一个明确的教学假设：三类来源分别有 800、150 和 50 百万个可用 token，合计十亿。直接连接后，它们的 token 占比才是 \(0.8,0.15,0.05\)。

    一个来源占比较大，不一定表示它更有价值；它也可能只是更容易获得。另一方面，简单地给每个来源同样多的训练机会，也不一定更好：少量内容可能因此被反复读取。配方需要同时回答能力覆盖与重复使用两个问题，而不是只追求看起来均衡的百分比。

    先说明抽样的单位¶

    “代码占 20%”至少有三种解释：20% 的文档、20% 的窗口，或20% 的有效训练位置。它们只有在额外条件成立时才相同。

    设每次先选择一个来源，再从该来源抽取一个窗口。若所有窗口都恰好包含 \(L\) 个有效目标，那么来源选择概率 \(p_j\) 也决定长期有效 token 比例。若来源 \(j\) 每个窗口平均只有 \(k_j\) 个有效目标，来源在有效 token 中的比例则为

    \[ q_j=\frac{p_j k_j}{\sum_i p_i k_i}. \]

    这个式子来自计数：进行 \(n\) 次选择时，来源 \(j\) 期望被选 \(np_j\) 次，贡献约 \(np_jk_j\) 个有效位置；再除以所有来源的总量。分子分母中的 \(n\) 抵消了。

    例如，两类来源被各选一半，但第一类每窗有 100 个有效位置，第二类只有 25 个，则有效 token 比例是 \(50/(50+12.5)=80\%\) 和 \(20\%\)。这里没有采样器错误，错误在于把“窗口一半”当作“有效 token 一半”。因此配方和消费报告必须写清计量单位。

    用一个指数控制来源比例¶

    先把来源 token 数归一化：

    \[ w_j=\frac{N_j}{\sum_i N_i}. \]

    其中 \(N_j\) 是来源 \(j\) 的可用 token 数。若希望减少大来源的优势，可以采用明确的幂指数约定

    \[ p_j(\alpha)=\frac{w_j^\alpha}{\sum_i w_i^\alpha}, \qquad \alpha>0. \]

    我们把 \(\alpha\) 称为混合指数，不使用含义可能相反的“温度”简称。取 \(\alpha=1\) 时保留原始比例；取 \(0<\alpha<1\) 时压缩大小来源的差距；取 \(\alpha>1\) 时放大差距。对两个正权重来源，有

    \[ \frac{p_i}{p_j}=\left(\frac{w_i}{w_j}\right)^\alpha. \]

    因此，当 \(w_i>w_j\) 且 \(0<\alpha<1\) 时，新比值比原比值小，但大来源仍然更大。当 \(\alpha\) 从正侧趋于零时，所有有数据的来源趋向均匀；没有数据的来源仍不能被采样。

    对刚才的 \(w=(0.8,0.15,0.05)\)，取 \(\alpha=0.5\)，得到

    \[ w^\alpha\approx(0.8944,0.3873,0.2236),\qquad p\approx(0.5942,0.2573,0.1485). \]

    书籍的目标比例从 5% 提高到了约 14.85%。代价也能算出来：若训练总预算仍为十亿 token、书籍只有五千万 token，那么按这个比例消费书籍约需 1.485 亿 token，相当于其可用量的 2.97 倍。这是平均覆盖量的估计；随机窗口会重叠，不能理解成每个位置都恰好读取三次。

    有些软件采用 \(w_j^{1/T}\) 的温度定义。它与这里的 \(\alpha\) 互为倒数，\(T<1\) 的方向恰好相反。复现实验应记录完整公式和参数，不能只写“温度 0.5”。

    预算与来源耗尽¶

    设总有效 token 预算为 \(N_{\mathrm{budget}}\)，理想的来源预算为 \(q_jN_{\mathrm{budget}}\)。当它超过可用数据量时，需要预先选择行为：停止整个训练；允许重复抽样；或者在剩余来源之间重新归一化。

    三种选择会产生不同实验。提前停止会改变总预算；重复抽样会改变重复率；重新归一化会改变后期分布。只有在这些规则固定后，配方才足以定义一个可解释的运行。不能在某个来源耗尽后静默切换到另一个来源，再把原始配方写进结果表。

    实际日志应分别记录抽到的窗口数、输入 token 数和有效 mask 权重总和。若 mask 是 0/1，最后一项就是有效位置数；若使用分数权重，则应称为权重总和。来源归属也需要保留：跨来源拼接窗口不能仅根据第一个 token 的来源给整窗贴标签。

    一次能手算、也能保存的配方计算¶

    当前训练器从一个逻辑 token 流抽窗口，尚未接入来源级混合采样器。下面是在目标 Linux 机器上运行的独立配方计算：它保存上述算例，不会修改训练行为。先完成环境章，再在仓库根目录执行。

    .venv/bin/python - <<'PY'
import json
from pathlib import Path

counts = {"web": 800_000_000, "code": 150_000_000, "books": 50_000_000}
alpha = 0.5
total = sum(counts.values())
weights = {name: (count / total) ** alpha for name, count in counts.items()}
normalizer = sum(weights.values())
recipe = {
    "kind": "teaching_plan_not_connected_to_trainer",
    "formula": "p_j = (N_j / sum(N)) ** alpha / sum_i((N_i / sum(N)) ** alpha)",
    "alpha": alpha,
    "selection_unit": "equal_valid_length_window",
    "target_tokens": 1_000_000_000,
    "exhaustion_policy": "with_replacement",
    "sources": [
        {"name": name, "available_tokens": counts[name], "probability": value / normalizer}
        for name, value in weights.items()
    ],
}
path = Path("outputs/mixture-example/recipe.json")
path.parent.mkdir(parents=True, exist_ok=True)
path.write_text(json.dumps(recipe, indent=2) + "\n", encoding="utf-8")
for source in recipe["sources"]:
    print(source["name"], f'{source["probability"]:.4f}')
PY

    按上式计算，打印值应依次约为 0.5942、0.2573 和 0.1485。生成的 JSON 可以用于核对公式与预算；它不是训练器已经执行该配方的证据。要完成真正的混合实验，还需要让采样器消费这份定义，并在训练记录中保存实际消费量。

    为什么短期比例会波动¶

    即使一个来源的选择概率是 \(p=0.2\)，也不意味着每五次必定选它一次。假设 \(n\) 次来源选择相互独立，每次概率不变。令 \(I_k\) 表示第 \(k\) 次是否选中该来源，选中为 1，否则为 0。样本比例为

    \[ \hat p=\frac{1}{n}\sum_{k=1}^{n} I_k. \]

    因为 \(\mathbb{E}[I_k]=p\)、\(\operatorname{Var}(I_k)=p(1-p)\)，独立性使方差相加，于是

    \[ \mathbb{E}[\hat p]=p,\qquad \operatorname{Var}(\hat p)=\frac{p(1-p)}{n}. \]

    当 \(n=100\) 时，标准差为 0.04，即四个百分点。一次观察到 17% 并不足以证明采样器错误。这一计算针对独立的来源选择次数；不能把同一窗口内相互关联的 1,000 个 token 当成 1,000 次独立抽样。

    分布式训练如何恢复同一个计划¶

    多张 GPU 上的进程需要知道各自负责哪些样本。可以用全局样本编号决定来源和窗口，再把互不重叠的编号分给各进程：

    \[ (\text{来源},\text{窗口起点}) =f(\text{seed},\text{配方版本},\text{数据版本},\text{样本编号}). \]

    这描述的是一个待实现的来源级设计。现有代码已经有单流窗口的无状态采样入口，但没有完整的来源选择、耗尽处理与消费日志。恢复时，除了 step，还必须保持上述函数及其版本、数据指纹、全局 batch 和编号分配一致；仅仅恢复一个整数 step 并不够。

    检查恢复正确性时，应对比“连续运行”和“中断后恢复”生成的来源与起点序列。样本编号不能跳过或重复；有放回采样却允许不同编号选到同一个窗口，不能把这种合法重访误判成恢复错误。下一章会把这些配方、数据和模型条件放到一次训练前验收中。
