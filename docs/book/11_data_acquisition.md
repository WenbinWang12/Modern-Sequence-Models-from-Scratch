# 5　获取语料与记录来源

## 为什么不从下载命令开始

假设我们用同一个 URL 下载了两次数据。文件名没变，但发布方补充了一批文档，重新打包并修正了元数据。两次训练都写着“使用 dataset-a”，loss 却不同。没有固定版本和摘要，我们无法判断差异来自模型还是语料。

获取数据首先要回答“我们在保存什么对象”。下载地址是位置，发布版本是身份，文件摘要是内容检查。这三者各自解决一个问题，不应把其中一个当成另外两个。

本书不在这里推荐一个必须购买或下载的大语料。我们先用仓库内原创教学文本演示接口；正式数据选择应服从目标语言、领域、预算和发布范围。这样读者可以先走通方法，再替换输入，而不是在开篇就受制于大规模存储。

## 来源清单和文件清单分开

来源记录描述发布方和获取方式，文件清单描述这次实际拿到的对象。一个来源可以有多个文件，一个压缩包也可能包含多个子来源。把二者塞进一行字符串，后面按来源统计时就会出现歧义。

一个来源记录可以这样组织：

~~~json
{
  "source_id": "source-a",
  "publisher": "<publisher>",
  "source_url": "<canonical-page>",
  "release": "<immutable-release>",
  "retrieved_at": "<UTC-time>",
  "terms_snapshot": "<saved-terms-path-or-digest>",
  "files": [
    {"name": "part-000.jsonl.gz", "bytes": 12345, "sha256": "<computed>"}
  ]
}
~~~

这个结构是治理示例，不是当前 `TokenDataset` 的输入格式。训练 loader 需要的是前一章介绍的 token manifest；来源清单留在数据处理记录中，通过版本关系与它关联。

对于会更新的远端资源，发布方提供的 commit、revision 或 snapshot 优先于“latest”。ETag 可以辅助缓存判断，但不能不加说明地当成 SHA256；不同服务的 ETag 语义并不相同。

## 下载完成不等于内容可用

文件完整性检查和文本抽取检查是不同阶段。压缩包 hash 正确，仍可能因为抽取器版本不同而生成不同文本。例如 HTML 抽取器是否保留标题、表格和代码块，会改变模型实际看到的上下文。

因此我们保存原始对象而不直接覆盖它。清洗后的文件写到新目录，记录抽取器版本、输入摘要和输出摘要。抽取失败时可以定位原文件和文档，而不需要重新访问可能已经变化的网站。

失败重试也应记录清楚。一次下载超时可以重试，但不能在报告中把没下载成功的分片当成“被质量过滤删除”。下载失败、解析失败和内容过滤属于不同损耗，它们会导致不同偏差。

## 来源、许可与可公开范围

每个来源需要记录可核对的条款依据，包括数据集页面、附带许可证以及特殊约束。这里的工程要求是保留事实和审核结论，不是用一个模板自动作法律判断。未知条款应保留为未知，而不是为了让流水线继续运行而填上宽松许可。

还要区分计划发布的对象：原始文件、清洗文本、token 分片、处理脚本和模型权重并不是同一份产物。一个“可以使用但不能再分发原文”的来源，可能影响复现方式；项目需要解释别人如何在有权限的环境重建相同输入。

同样，删除个人信息的规则、对第三方代码的处理和 benchmark 污染检查都要分开描述。许可字段存在，并不证明这些审查已经完成；后面章节也不会用去重代替它们。

## 用数量把获取阶段讲清楚

考虑一个纯教学例子：来源列表宣称有 1,000 个文件，我们成功下载 990 个，其中 980 个能解析。解析得到 10 万条记录，有 500 条缺少正文。最终交给清洗阶段的是 99,500 条文档。

如果只报告“获得了 99,500 篇文档”，我们看不出 10 个未下载文件和 10 个无法解析文件是否集中在某种语言或格式。一个小比例的损耗，也可能对某个小来源形成很大偏差。

来源报告应保留从文件到文档的数量链，并按来源、语言和格式分组。数量对不上时，先修报告，不要继续调模型。否则后面的保留率是在一个已经不完整的分母上计算的。

## 仓库中的实践边界

`examples/book/clean_corpus.jsonl` 是人工整理的教学输入，目的是演示数据格式。`ttt.data` 只负责把支持的文本字段编码，并不包含网页抓取、许可证判定或通用正文抽取器。

因此，替换正式语料时应在 `ttt.data` 之前完成获取、抽取和来源记录。保持训练入口简单是合理的，但上游必须有自己的版本和报告，不能因为训练模块没读那些字段就把它们丢掉。
