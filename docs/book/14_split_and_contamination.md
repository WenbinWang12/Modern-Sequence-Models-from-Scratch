# 8　划分训练集，并定义什么叫“未见数据”

## 随机切分为什么不总是足够

若一套语料包含同一教程的十个镜像，把每个文档独立随机分到训练和验证，就可能让两边都出现相关文本。这个风险取决于切分比例，不能笼统地说“几乎必然”。设每条记录进入验证集的概率为 \(p\)，十条全部进训练的概率为 \((1-p)^{10}\)，全部进验证的概率为 \(p^{10}\)。排除这两种情况，重复簇横跨两边的概率为

$$
P(\text{跨集合})=1-(1-p)^{10}-p^{10}.
$$

当 \(p=0.01\) 时，它约为 \(9.56\%\)；当 \(p=0.1\) 时，约为 \(65.13\%\)。即使单个簇的风险不高，大量重复簇仍可能造成污染。文件名不重叠，并不保证内容没有重叠。

先问评估目标。如果我们希望预测同类来源的新文档，可以按文档簇切分；如果希望检验未来新闻，按时间切分更有意义；如果希望检验未见代码项目，则需要项目级边界。没有一种切分能同时回答所有问题。

因此“验证集大小 1%”只是比例，完整协议还包括单位、时间、来源和关联规则。一个比另一个更低的验证 loss，只有在评估分布明确时才有解释。

## 把相关样本留在一起

用 `split_group` 表示共同归属，例如重复簇 ID、书籍 ID 或代码仓库 ID。稳定 hash 可以让新增文档不改变已有组的切分：

~~~python
import hashlib

def choose_split(group_id):
    digest = hashlib.sha256(group_id.encode("utf-8")).digest()
    bucket = int.from_bytes(digest[:8], "big") % 10_000
    if bucket < 100:
        return "test"
    if bucket < 300:
        return "validation"
    return "train"
~~~

这个示例给每组固定归属，期望比例约为 1%、2%、97%，但不保证 token 比例精确相等。一组超长书籍可能让比例明显偏移。`hash()` 不适合代替这里的 SHA256，因为进程间的默认 hash 行为可能不同。

hash 切分的稳定性依赖 group ID 稳定。若先用文件遍历序号生成 ID，改变并行度就可能改变分组；这时稳定 hash 只是把不稳定输入变成稳定-looking 输出。

## 为什么应在 tokenization 和 packing 前切分

如果把所有文档拼成 token 流再抽 1% 给验证，相邻窗口可能共享大量文本。长度 1,024 的两个窗口只偏移一个 token，就会有 1,023 token 重叠。这样的验证显然很难代表未见数据。

更清楚的顺序是：文档归组，按组切分，分别编码，再生成各自 manifest。物理 shard 可以切开文档，但不同集合的输入不能先混合后分片。训练的随机窗口也不能跨越 train 与 validation 的逻辑流。

当前 loader 可以读取一个 manifest 中的连续 token，但并不会替我们创建训练/验证集合。这个边界必须在准备输入时建立。

## 污染检测是另一层比较

去重寻找训练语料内部的重复，污染检测比较训练输入与评估对象。可以用全文 exact match、长子串、规范化题干或近似匹配产生候选，再结合任务单位审核。

例如一道数学题改了人名和数字，字节 hash 无法识别；一段常见定义在许多地方出现，也不必然说明完整题目泄漏。我们需要记录匹配方式和匹配范围，而不是把所有候选一律解释成污染。

评估协议也包含调参接触。反复查看某个集合并选择模型，会让它逐渐承担开发集角色。保留一个冻结测试集，就是为最终结论留出没有反复参与选择的证据。

## 一个切分报告怎样暴露问题

想象验证集只占文档的 2%，却占 token 的 18%。这可能是长文档簇集中落入验证，也可能是错误的分组。先查看长度分位数和来源表，再决定是否调整。

另一个例子是训练与验证 exact overlap 为零，但同域名、同模板的文档很多。这个报告仍不足以声称“无污染”。应说明已经检查的范围，以及未覆盖的近似或语义关系。

正式报告至少列：每组文档数与 token 数、语言和来源分布、组间交集、匹配候选数量、人工审核结论、规则版本与输入摘要。它提供的是有边界的证据，不是对所有未知评测的绝对保证。

## 本章最小检查、预期证据与失败诊断

切分后的两个 JSONL 必须分别生成 manifest：

~~~bash
.venv/bin/python -m ttt.data \
  --input <train-jsonl> \
  --output outputs/split-train \
  --sharded --tokenizer byte --shard-tokens 256
.venv/bin/python -m ttt.data \
  --input <validation-jsonl> \
  --output outputs/split-validation \
  --sharded --tokenizer byte --shard-tokens 256
~~~

上述编码命令生成两个独立的 <code>manifest.json</code>，不会生成切分或污染报告。上游切分过程还需另外保存组数、文档数、token 数、来源分布、候选匹配和人工审核结果。检查的是两个集合中的文档摘要或 group ID 是否重叠，而不是只比较两个 manifest 是否相同；验证 loss 较低不能抵消污染。

## 本章小结与下一问

切分单位必须与评估问题一致：文档簇、项目、时间或任务对象。Exact overlap 为零只排除了最窄的一类重复，不能声称没有近似或语义污染。下一章固定每个 split 的 tokenizer 和词表，进入 token ID 与输出头。
