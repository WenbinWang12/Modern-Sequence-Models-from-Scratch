# 14. 数据切分与污染检查

## 切分的目的

验证集不是训练集随机抽出的几行，而是用来回答“模型对未参与优化的数据如何表现”。如果相似文档、同一作者的版本或同一网页镜像被拆到不同集合，验证 loss 就会高估泛化能力。

切分策略应与数据来源和任务目标相匹配。对时间变化的语料，时间切分可以模拟未来数据；对多来源语料，按来源或文档簇切分更能避免近重复泄漏。

## 四个需要固定的单位

| 单位 | 适用情况 | 风险 |
|---|---|---|
| 文档 | 普通网页、书籍、代码文件 | 长文档内部仍可能跨集合 |
| 文档簇 | 近似去重后保留的相似集合 | 需要稳定簇 id |
| 时间 | 新闻、版本化代码 | 早期数据分布可能不同 |
| token | 已经只有 token shard 的情况 | 容易把相邻文本拆开 |

默认先按文档或文档簇切分，再进行 tokenizer 和 packing。这样同一篇文档不会因为切块而跨越集合。

## 污染报告

训练前至少生成：

- 各集合的文档数和 token 数；
- 按来源、语言、领域和长度的分布；
- 训练与验证的 exact/near match 数；
- 与公开评测集的匹配计数；
- 切分 seed、规则、代码 commit 和输入 manifest。

污染检查结果应有明确状态：pass、review 或 blocked。review 表示发现了需要人工判断的匹配，不能在汇总图表里当成通过。

## 评测集的时间边界

公开 benchmark 会更新，仓库应记录使用的版本和下载日期。若 benchmark 内容被用于 tokenizer 训练、去重索引或调参，也应写入污染声明。调参阶段看过验证集后，最终测试集只能用于一次冻结评估。
