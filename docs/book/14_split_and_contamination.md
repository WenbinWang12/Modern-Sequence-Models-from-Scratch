# 8　划分训练集，并定义什么叫“未见数据”

## 为什么训练得更好，不一定意味着学得更好

老师让学生做十道练习题，第二天用原来的十道题考试。学生得了满分，我们能据此判断他已经掌握这一类问题吗？不能排除他只是记住了答案。换成十道不同但考查相同知识的题目，才更接近我们真正关心的能力。

训练语言模型也有类似问题。训练集中的文本参与参数更新；模型反复接触这些内容，训练损失下降本来就是优化的目标。**验证集**用来观察模型对没有直接参与参数更新的数据表现如何，并帮助我们选择配置、训练步数和清洗规则。**测试集**则为已经确定的方案提供最终评估，原则上不反复参与这些选择。

这三个名称描述数据在实验中的角色，而不是三个任意的文件夹。如果我们反复查看“测试集”上的分数来选择模型，它实际上已经承担了验证集的作用。即使没有把它送进反向传播，选择过程也接触了它的信息。因此，“未见”既包括没有直接训练，也包括明确限制哪些开发决策可以使用这份数据。

语言模型通常通过预测正文中的下一个 token 来计算损失，验证和测试也可以沿用这一目标。本章先处理文档的归属，不需要读者已经知道 token 的具体算法；下一章会完整介绍文本如何变成 token。此时最重要的是建立边界：哪些完整文档能够参与训练，哪些保留给评估。

## 切分单位应由想回答的问题决定

“随机取 1% 做验证”只指定了比例，没有说明抽取什么。如果同一本书拆成了许多章节，这些章节是否应该独立抽样？如果一篇文章被十个网站转载，十个 URL 是否就是十个独立对象？答案取决于我们希望证明什么。

| 希望评估的能力 | 应考虑共同归属的单位 | 需要防止的混淆 |
|---|---|---|
| 阅读同类来源的新文档 | 原文及其重复、近重复版本 | 训练见过文章的镜像 |
| 阅读没有见过的书籍 | 书籍 | 同一本书的相邻章节跨集合 |
| 处理新的代码项目 | 仓库或项目 | 同项目文件和分支跨集合 |
| 预测未来时段的文本 | 时间边界及相关文档组 | 训练使用了未来信息 |

这不是一张自动执行的规则表。例如，时间切分需要同时处理旧文章在未来被转载的问题，项目切分需要识别复制来的代码。我们首先定义评估目标，然后据此建立关联组，最后才选择比例。

前一章的去重可以为此提供线索，但“保留哪些文档”与“哪些文档不能跨集合”是两个决定。一组有共同来源、并且互相补充的文档可以全部保留，同时必须进入同一个集合。切分组通常可以比删除重复时使用的相似条件更宽。

## 独立切分镜像为什么会泄漏

设同一篇文章有 \(m\) 个镜像，每条记录独立地以概率 \(p\) 进入验证集，以概率 \(1-p\) 进入训练集。这里先只考虑两个集合，使概率推导清楚。

这组记录不跨集合只有两种情况：全部进入训练，或者全部进入验证。独立性意味着联合概率可以相乘，因此两种情况的概率分别为 \((1-p)^m\) 和 \(p^m\)。它们互斥，不可能同时发生。于是

$$
P(\text{重复组跨越训练与验证})
=1-(1-p)^m-p^m.
$$

取 \(m=10\)。当 \(p=0.01\) 时，跨集合概率约为 \(9.56\%\)；当 \(p=0.1\) 时，约为 \(65.13\%\)。所以风险与组大小和切分比例有关，不能笼统地说每组“几乎一定泄漏”。但只要语料里有很多这样的组，少量的单组风险也值得认真处理。

这个计算还解释了按组切分的作用：我们只对整组作一次分配，并让组内记录继承它的结果。这样，在分组信息正确的前提下，该组跨集合的概率就是零。它不能保证我们已经发现所有镜像；分组遗漏仍然可能造成泄漏。

## 给每组一个稳定的归属

仓库的小实验在每条记录中添加 `split_group`。例如，`d01` 和 `d02` 是相同短文的两个来源版本，组名都是 `guide-blue`；`d04` 和 `d05` 是两条不同的项目说明，组名都是 `project-cache`。这两种组分别展示“重复关系”和“共同项目关系”。

我们希望分配具备两个性质：改变文件的遍历顺序，不改变已有组的集合；新增一个无关组，不重新洗牌全部旧数据。一个直接方法是对稳定组 ID 计算固定摘要，再将摘要映射到编号桶。**桶**在这里只是 0 到 9,999 中的一个整数。

教学脚本的核心代码是：

~~~python
payload = json.dumps(
    ["book-group-split-v1", seed, group],
    ensure_ascii=False, separators=(",", ":"),
).encode("utf-8")
bucket = int.from_bytes(hashlib.sha256(payload).digest()[:8], "big") % 10_000
~~~

第一步将规则名、种子和组 ID 序列化。明确字段边界很重要：如果只直接拼接字符串，`"ab" + "c"` 与 `"a" + "bc"` 会变成相同输入。第二步用 SHA-256 产生摘要，取前 8 字节，并按大端顺序解释成非负整数；大端表示靠前的字节承担较高位。最后的取余运算把整数落到 10,000 个桶之一。

`seed` 是这套确定性分配的输入之一。相同输入必然得到相同桶；改变种子会定义另一套分配。这里不使用 Python 内置的 `hash()`，因为字符串和字节的哈希默认带有进程间可变的随机化，不能直接作为持久切分规则。参见 [Python 对 `__hash__` 的说明](https://docs.python.org/3.12/reference/datamodel.html#object.__hash__)。

本例规定桶号小于 6,000 的组进入训练，6,000 到 7,999 进入验证，其余进入测试。**60% / 20% / 20% 只是让十个小组有机会展示三个集合的教学比例**，不是正式预训练的推荐比例。取模也不是严格的均匀采样，因为 \(2^{64}\) 不能被 10,000 整除；在把摘要视为均匀 64 位值的近似下，各桶概率只有极小差异。稳定性来自确定性输入，近似比例则还依赖输入组与摘要分布，二者不要混为一谈。

这个方法也有明确边界。组 ID 如果来自不稳定的文件遍历序号，改变遍历顺序仍会改变结果；新增文档如果揭示了两个旧组其实应合并，也可能需要重新处理它们的归属。所谓“新增不影响已有分配”，指规则和已有组 ID 保持不变、添加新的独立组，而不是承诺任意数据修订都不会改变切分。

## 组比例、文档比例与 token 比例并不相同

对组近似均匀分配，不会使每个集合恰好拥有固定比例的文档。我们可以用一个小推导理解原因。令 \(I_g\) 表示组 \(g\) 是否进入验证集：进入时为 1，否则为 0；令 \(w_g\) 表示该组的文档数量。验证文档总数为

$$
N_{\mathrm{val}}=\sum_g w_g I_g.
$$

在理想化模型中，每组以概率 \(p\) 独立进入验证集。因为 \(I_g\) 以概率 \(p\) 取 1，它的平均值是 \(p\)。期望的线性性质给出

$$
\mathbb E[N_{\mathrm{val}}]=p\sum_g w_g.
$$

这说明长期平均比例符合设计，**不说明某一次切分恰好如此**。要描述不同切分结果相对平均值的波动，我们使用方差。对于一个随机数量 \(Z\)，定义 \(\operatorname{Var}(Z)=\mathbb E[(Z-\mathbb E[Z])^2]\)：先算每次结果与平均值的距离，平方后再取平均。平方让正负偏差不相互抵消；方差越大，结果通常越分散。若 \(Z\) 的单位是文档数，方差的单位就是文档数的平方。

由于 \(I_g^2=I_g\)，有
\(\operatorname{Var}(I_g)=\mathbb E[I_g^2]-\mathbb E[I_g]^2=p(1-p)\)。
乘以固定权重 \(w_g\) 会让每次偏差也乘以 \(w_g\)，所以平方偏差乘以 \(w_g^2\)，即 \(\operatorname{Var}(w_g I_g)=w_g^2\operatorname{Var}(I_g)\)。组间独立时，这些加权项的方差可以相加：

$$
\operatorname{Var}(N_{\mathrm{val}})
=p(1-p)\sum_g w_g^2.
$$

平方项解释了大组的影响。假设仅有两个组，分别包含 90 和 10 篇文档，且 \(p=0.2\)。期望验证文档数为 20，但一次切分只能得到 0、10、90 或 100 篇，根本不可能恰好得到 20 篇。把 \(w_g\) 换成该组固定 tokenizer 下的 token 数，推导仍成立；这时长书籍的影响可能更明显。这是独立随机分组的分析模型，不是对固定 SHA-256 输出作随机性证明。

因此，切分后至少同时报告组数、文档数和长度规模。正式项目在 tokenizer 固定后补充 token 数；本章 tokenizer 还未确定，脚本先报告正文 UTF-8 字节数。它没有把字节数冒充 token 数，也没有把 JSON 字段名和序列化开销算进“正文长度”。

## 运行一次带有故障对照的切分

教学输入在 `examples/book/fixtures/split_records.jsonl`。其中有 12 条文档、10 个组，两组各含两篇；另外有一条较长的正文，用来提醒我们数量和长度不是同一件事。运行：

~~~bash
.venv/bin/python examples/book/split_walkthrough.py \
  --output outputs/book-split-v1 --seed 17
~~~

脚本只使用标准库，输出 `train.jsonl`、`validation.jsonl`、`test.jsonl` 和 `split-report.json`。它不训练模型，也不会根据模型分数挑选种子。报告中的 `groups` 列出每组的桶号和归属；`totals` 列出每个集合的组数、文档数、正文 UTF-8 字节数及输出文件摘要。三份文档数之和应为 12，组数之和应为 10；每个集合的实际比例以该次报告为准。

脚本还会改变输入遍历顺序，并增加一个全新的组，重新计算归属。通过后，报告中出现：

~~~json
{
  "order_independent": true,
  "existing_assignments_stable_after_append": true
}
~~~

仅仅输出三个文件还不足以证明检查器有效。为此，脚本在内存中另外构造两种有意出错的输入：

| 故障对照 | 故意做什么 | 应触发的检查 |
|---|---|---|
| 同组跨集合 | 将多文档组中的一篇移到另一个集合 | `group_leak` |
| 异组相同正文 | 保持组归属不变，把另一集合的一篇正文替换为相同文本 | `normalized_content_leak` |

第一种验证组边界，第二种验证内容边界。如果检查器没有拒绝故障输入，脚本直接失败；这些故障版本不会写进正常的三份 JSONL。`failure_probes` 记录捕获的原因，不能只看到英文单词 `error` 就误认为正常切分失败。

内容检查先做 NFC 规范化，再比较完整正文的 SHA-256。这可以发现本例中的全文重复，但不会发现只共享一段内容、换了人名数字或经过改写的题目。严格说，摘要碰撞也可能带来误报；本例将摘要重合视为需要拦截的信号，不把它当作语义判断。报告的 `scope` 明确限制为按组切分和 NFC 全文摘要重叠。

重复运行需换一个未存在的输出目录，以免覆盖先前证据。修改 `--input` 时，还需保留至少一个多文档组和至少两个非空集合，否则没有条件演示本章的两种故障；程序会明确拒绝，而不是伪造一份“已验证”的结果。

输入中的额外元数据会随文档保留，因此它们也必须能写成有效 JSON。本例拒绝 `NaN`、`Infinity` 以及超出有限浮点数范围的数字，例如 `1e999`；任意层级出现这些值都会使整个切分在创建输出目录前停止。`1e999` 本身符合 JSON 数字语法，这里的拒绝属于本例读取器的数值范围限制，不能解释为语法错误。

## 在编码和 packing 之前建立边界

切分后的文档才应进入各自的编码流程。如果先把所有正文拼成一个 token 流，再抽窗口分配给训练与验证，两个窗口可能共享大量内容：长度 1,024 的窗口只偏移一个位置，就会重叠 1,023 个 token。这两个训练实例不是两份独立证据。

更清楚的顺序是：确定关联组，完成切分，分别编码，再分别生成训练和验证 manifest。当前 `TokenDataset` 可以读取一份 manifest 所描述的连续 token，但不会自动替我们建立训练、验证和测试边界。前面的脚本已经输出可用的 JSONL，后续编码可以直接读取相应文件；不要重新合并三个集合再统一抽窗口。

tokenizer 自身也是从数据中学习的程序。若实验目标是严格保留未见数据，训练 tokenizer 所用文本也应限制在训练集合；验证和测试共用这个冻结的 tokenizer。下一章会区分“训练 tokenizer”与“用 tokenizer 编码”，这两步不应混淆。

## “没有发现重复”应该怎样表述

去重主要比较训练语料内部的文档；评估污染检查比较训练输入与评估对象。二者可以复用某些匹配方法，但比较范围不同。一份训练集内部没有重复，不代表其中没有某个 benchmark 的题目或答案。

检查可以从全文匹配开始，再按需要增加长子串、规范化题干或近似匹配。每种方法都有覆盖范围：短小的公共定义可能产生误报，改写后的题目可能漏报。报告应保存候选、匹配位置、比较单位和审核结论，并说明哪些方法没有实施。

本章脚本通过后，恰当的结论是：“这些组没有跨集合，检查范围内没有跨集合的 NFC 全文摘要重叠，两个故障对照被拒绝。”它不支持“数据已经无污染”，更不支持对未来所有评测的保证。这个小语料也不足以判断泛化能力；它检验的是切分机制是否按约定执行。

我们现在固定了文档可以进入哪个集合。下一章研究另一个会改变训练结果的选择：同一段正文怎样变成整数序列，以及词表和分词方式如何影响模型的输入、输出与计算量。
