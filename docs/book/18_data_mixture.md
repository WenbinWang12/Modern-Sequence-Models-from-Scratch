# 12　数据混合：训练配方不是文件大小

## 为什么直接拼文件会产生偏差

假设网页有 900 GB，代码有 50 GB，书籍有 50 GB。把三者拼成一个流，模型大约 90% 的 token 来自网页。这个比例可能是合理的，也可能完全不符合研究目标，但它不是“自然发生的客观比例”，而是文件容量替我们做的选择。

另一个极端是每个来源按文档均匀采样。短代码片段和长书籍章节会获得不同的 token 权重。我们要先选择目标分布，再选择一个 sampler 实现它。

## 从 token 预算写配方

一个配方示例：

~~~json
{
  "sources": [
    {"name": "web", "weight": 0.70},
    {"name": "code", "weight": 0.20},
    {"name": "books", "weight": 0.10}
  ],
  "sampling": "temperature",
  "temperature": 0.7,
  "seed": 17,
  "target_tokens": 1000000000
}
~~~

`weight` 是目标抽样概率，不保证最终严格命中。来源可能提前耗尽，清洗后可用量也会改变。若使用温度采样，可按原始权重的幂重新归一化；温度小于 1 会提高小来源的相对权重，但具体公式和耗尽策略必须写入实现。

数据混合应至少有两张表：配方表描述计划，消费表描述实际。消费表按有效 token 统计，而不是只按 batch 次数，因为 mask、padding 和丢弃样本会改变有效量。

## 一个温度采样的算例

设三个来源的原始权重为 \([0.8, 0.15, 0.05]\)，温度 \(\tau=0.5\)，用 \(w_i^{1/\tau}\) 作为新权重，得到 \([0.64, 0.0225, 0.0025]\)，归一化后小来源反而更低。这说明“温度采样”不能脱离公式讲；有些系统使用 \(w_i^\tau\)，方向相反。

若目标是提升小来源，采用 \(w_i^\tau\) 且 \(\tau<1\) 的约定，示意值为 \([0.894,0.387,0.224]\)，归一化后分别约为 59.4%、25.7%、14.9%。这些数只用于说明公式，不能当成仓库默认配方。

## 确定性要落到 rank 和恢复

单机 sampler 保存 seed 和 RNG state 已经不够分布式使用。多个 rank 需要决定：先全局抽来源再按 rank 分发，还是每个 rank 独立抽样；两者会产生不同重复率和通信量。

更稳妥的设计是从全局 sample index 派生来源和窗口，再让 rank 取自己的索引。这样恢复时只要恢复全局 step，就能重建各 rank 的数据顺序。当前仓库的 `BatchStream` 是单一 token 流随机窗口，并没有实现来源级混合 sampler；本章的配方是下一阶段设计，不应被写成当前功能。

## 如何验证混合比例

训练前，固定 seed 生成一段不更新模型的 sample plan，统计每个来源的目标与实际 token。训练中累计记录来源 token、mask 有效 token和丢弃 token。恢复后，把恢复前后的 sample index 拼接，检查是否出现重复或跳跃。

还要看短期窗口的波动。总体 70/20/10 不代表每个 1,000 token 的小批量都接近这个比例；小来源在短窗口里可能有较大方差。报告可同时给累计比例和滑动窗口区间。

## 本章最小检查、预期证据与失败诊断

当前仓库没有来源级混合 sampler，因此先把配方保存为 JSON，再检查它是否能被实验读取：

~~~bash
python -c "import json; p='outputs/recipe.json'; print(json.dumps(json.load(open(p, encoding='utf-8')), ensure_ascii=False, indent=2))"
~~~

成功输出只能证明 recipe 文件可解析。真正的混合实验还必须记录每个来源的目标 token、实际 token、有效 mask token、sample index 和恢复前后是否重复；如果只有权重而没有消费日志，不能声称模型使用了该配方。

## 本章小结与下一问

混合配方是显式概率分布和 token 预算，不是文件大小的副产品。温度公式必须写明约定，rank 和恢复协议必须从全局 sample index 定义。下一章把 tokenizer、manifest、mask 和 recipe 放进训练前验收。
