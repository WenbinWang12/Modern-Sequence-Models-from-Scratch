# 书籍章节写作约定

本书的章节不是命令清单，也不是论文摘要。每章都围绕一个能被实验回答的问题组织正文。

## 叙事顺序

1. 先说明问题为什么会影响训练结果或系统成本；
2. 给出必要的概念、形状、状态或数学关系；
3. 指向仓库中真正实现这一关系的文件；
4. 给出在目标机器上可执行的最小命令；
5. 说明要保存哪些日志、报告和 checkpoint；
6. 以一个尚未解决、但会由下一章推进的问题收尾。

## 写作边界

每章只引入有限的变量。若命令改变了模型结构、数据、训练预算和硬件，应在正文中分别说明。不要把“代码运行成功”写成“方法有效”，也不要把估算的 FLOPs、未经验证的长上下文或尚未复现的论文结论写成最终结果。

中文和英文页面使用相同的章节编号、代码入口、实验语义和证据类型。语言可以自然调整，但不能让两版隐含不同的实验协议。

## 面向第一次接触基模训练的读者

默认读者没有完整学过机器学习、深度学习或分布式训练。每个重要概念第一次出现时，必须按下面的顺序展开：

1. **问题和直觉。** 先说明它解决什么困难，再用日常类比或一个最小例子解释它在系统中扮演的角色；
2. **具体例子。** 用很小的数字、短序列或一个真实代码输入走一遍，读者应能手算至少一个结果；
3. **正式定义。** 给出统一记号、变量的含义、张量形状、适用条件和边界情况；
4. **逐步推导。** 交叉熵、梯度、注意力、优化器、采样概率等公式不能只写结论，要解释每一项从哪里来，以及它和前一步的关系；
5. **代码映射。** 指出公式对应的函数、参数树、输入字段和输出字段，解释实现为什么按这个顺序执行；
6. **实验验证。** 给出最小可运行命令、应观察的日志、成功标准和一个可能失败的结果；
7. **边界与下一问。** 说明这一节证明了什么、没有证明什么，以及下一节要解决的剩余问题。

如果一个概念需要线性代数、概率论或优化知识，背景知识就在首次使用处补齐。可以先给一句不带公式的结论，再给严格形式；不能把“读者应该已经知道”当作跳过解释的理由。类比只能帮助建立直觉，随后必须明确类比在哪些地方失效。

## 数学排版

数学对象、变量、集合、概率和张量形状统一使用 LaTeX 行内或独立公式渲染，例如 \(x\)、\(\theta\)、\(P_{\mathrm{win}}\) 和

$$
\mathcal{L}(\theta)=\mathbb{E}[\ell(\theta)].
$$

反引号只保留给真实的代码字段、命令、路径、API 名称和 JSON key，例如 `input_ids`、`--resume` 和 `ttt/data.py`。首次连接代码和数学对象时，写成“代码字段 `input_ids` 对应数学记号 \(X\)”。

## 证据优先级

运行目录中的 JSON、JSONL、checkpoint 和机器报告优先于手工抄写的数字。书中文字解释证据能支持什么结论，也要明确哪些结论还没有被验证。

## 图表与双语出版规范

只要一章包含流程、状态转移、层次关系或对照实验，就应优先提供一张可导出的矢量图。图放在第一次解释该关系的位置，使用连续的“图 1、图 2……”编号，图注说明它回答的问题，`alt` 文本说明图的内容；主图源文件和网页 SVG 都提交到仓库。Mermaid 适合快速结构图，关键主线图使用统一视觉系统的 SVG 或 TikZ。

中英文页面共享图和实验协议，但各自拥有自然的图注、章节标题和链接。交稿前检查：章节编号、公式变量、代码入口、命令参数、图号、下一章链接和结论边界是否一一对应。英文版不能只保留中文章的摘要；每一章都应保留问题、原理、代码、实验、证据和下一步六个环节。

## 出版版固定章节骨架

除非某章明确说明原因，正文必须按下面的小节顺序组织。小节标题可以翻译，但两种语言的顺序和信息量必须相同。

1. **本章导读（Overview）**：用一个具体场景提出问题，说明本章解决什么、暂时不解决什么；
2. **预备知识与完成标准（Prerequisites and outcomes）**：列出读者需要的最少背景，并写出读完后能完成的一个动作；
3. **贯穿例子（Running example）**：使用与前后章节相同的短序列、tiny 配置或实验 ID，给出输入和预期输出；
4. **直觉与术语（Intuition）**：先用自然语言解释对象，再说明类比在哪些地方失效；
5. **正式定义（Formal statement）**：统一记号、变量、张量形状、状态 owner、输入输出和适用条件；
6. **逐步推导（Derivation）**：从上一行得到下一行，不能只展示最终公式；
7. **代码映射（Code map）**：列出函数、字段、参数树、输出文件，并解释执行顺序；
8. **最小运行（Runnable checkpoint）**：给出远端命令、资源前提、预计耗时或规模；
9. **预期证据与失败诊断（Evidence and failure diagnosis）**：说明成功输出、失败输出、先查哪个字段；
10. **局限、小结与下一问（Limitations, summary, next question）**：明确已证明、未证明和下一章的依赖。

每章至少有一个“读者可以手算的结果”、一个“读者可以检查的文件或字段”和一个“失败时不会误判为成功”的判据。只有概念而没有结果、只有命令而没有预期输出、只有图而没有读图任务，都不算完成。

## 段落审稿表

逐段审稿时，为每个非装饰性段落分配稳定 ID，并记录以下字段。代码块、公式、表格和图注也作为相邻段落审查，因为它们共同构成读者看到的论证。

| 字段 | 审稿问题 |
|---|---|
| Paragraph ID | 文件、章节、小节和段落序号是否唯一？ |
| Reader question | 这一段回答读者的哪个具体问题？ |
| Prerequisite | 首次出现的术语是否已补齐必要背景？ |
| Intuition example | 是否有短序列、数字、形状或失败场景？ |
| Formal statement | 变量、单位、张量形状和适用范围是否明确？ |
| Derivation | 结论是否从前一步逐步得到？ |
| Code symbol | 是否指向真实函数、字段、命令或输出文件？ |
| Runnable command | 读者能否在目标机器执行最小检查？ |
| Expected artifact | 是否说明日志、JSON、图或 checkpoint 应出现什么？ |
| Failure diagnosis | 失败时是否给出首个检查字段和常见原因？ |
| Limitation | 是否明确这段证据没有证明什么？ |
| Next question | 是否自然引向下一段或下一章？ |
| zh-en parity | 中文和英文是否保留同一事实、例子、公式和边界？ |

审稿结果使用三档：P0 表示会误导读者或使实验不可解释；P1 表示缺少出版级教学链条；P2 表示术语、图注、风格或可读性改进。一个章节只有在所有 P0/P1 清零，并且每个核心段落的表格字段都有证据或明确的“不适用”说明后，才可以进入下一轮。
